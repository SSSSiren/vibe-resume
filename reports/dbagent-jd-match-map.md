# DBAgent JD 匹配映射表

| JD 高频关键词 | 对应的项目证据 | 可以写进简历的表达 | 面试追问风险 | 建议准备的回答要点 |
|---|---|---|---|---|
| Agent / Agent 开发 | `04-deepagents-DBAgent` 使用 deepagents / LangGraph 接管通用 Agent 循环；项目保留工具适配、事件适配、上下文构建、NL2SQL、安全校验和评测边界。四阶段材料显示从 LangGraph 原型、SDK/MCP、手写 ReAct 到 deepagents 工程化演进。 | 手动实现面向 OneDBA 业务库的 Text2SQL Agent，支持多轮会话、工具调用、上下文注入、SQL 生成校验与流式响应。 | 容易被追问“你自研了 Agent 框架吗”“deepagents 做了什么”“为什么多次换框架”。 | 不说自研通用 Agent 框架。说明 deepagents 负责通用循环、消息状态和工具调度；DBAgent 负责业务工具、上下文、NL2SQL、安全和评测。阶段演进是为了解决原型规范化、SDK 黑盒、手写 ReAct 维护成本等问题。 |
| AI 应用开发 / LLM 应用工程 | 项目通过 OpenAI 兼容 API 调用 LLM，围绕 OneDBA 数据库查询场景落地自然语言查库、表结构理解、SQL 生成、执行和结果解释。 | 构建面向真实业务数据库的 AI 应用后端，将 LLM 能力接入数据库平台，完成自然语言查库的端到端工程闭环。 | 容易被追问“是否训练/微调模型”“是不是只是套 API”。 | 明确不是模型训练项目，而是 LLM 应用工程。重点讲业务流程拆解、工具边界、SQL 安全、上下文增强、评测与交付，而不是模型算法创新。 |
| Text2SQL / NL2SQL | `app/nl2sql/` 负责 SQL 生成、验证、修复；链路包括找库、找表、查 schema、生成 SQL、validator 校验、repair 修复、OneDBA 只读执行。 | 设计并实现 NL2SQL 工程链路，打通用户问题、schema 检索、SQL 生成、SQL 安全校验、失败修复和 OneDBA 只读执行。 | 容易被追问 SQL 正确性如何保证、是否支持复杂 JOIN、是否只是 prompt。 | 讲清三层保障：真实 schema 输入、validator 安全/字段/表名校验、执行反馈 repair。复杂 JOIN 和 SQL 规范仍是迭代点，不夸大为完全解决 Text2SQL。 |
| RAG / 知识库 / HDC | HDC 数据底座：OneDBA schema 采集 -> 列级语义 -> 表级描述 -> 库级摘要 -> 写入 OpenViking；在线按问题召回库/表/列上下文注入 Agent。 | 引入 HDC 数据底座，将数据库 schema 离线生成语义知识，在线检索后注入 Agent 上下文，减少陌生业务库下的找表和字段理解成本。 | 容易被追问“是不是 Graph RAG”“HDC 是否替代工具搜索”“召回质量如何评估”。 | 不写 Graph RAG。说明 HDC 是 schema 语义 RAG，提供前置线索，不替代 `find_table` / `describe_table` / schema 校验。评估看表/列引用、过滤条件、结果正确性和工具调用成本。 |
| Memory / 长短期记忆 | 项目包含会话历史、查询偏好、OpenViking 长期记忆、SQL Memory。SQL Memory 记录历史成功问题、SQL、表名、数据库、执行摘要和 embedding，并按相似度召回。 | 实现会话上下文、查询偏好和 SQL Memory 机制，通过历史成功 SQL 模式召回辅助相似查询生成。 | 容易被追问“SQL Memory 是不是缓存答案”“错误 SQL 进入记忆怎么办”“多用户隔离如何做”。 | 强调 SQL Memory 复用查询模式，不缓存答案；新问题仍要重新生成、校验、执行。准备说明 user/database scope、Admin 清理、re-embed、TTL/治理可作为后续优化。 |
| Tool Calling / Function Calling / Tool Use | 工具集包括 `list_databases`、`find_table`、`describe_table`、`query_database`、`execute_sql` 等；阶段 02 用 SDK/MCP 规范工具注册，阶段 04 用 Tool Adapter 适配 deepagents/LangChain。 | 封装数据库工具集并接入 Agent Tool Calling，支持数据库发现、表搜索、表结构查询、SQL 生成和只读执行。 | 容易被追问工具粒度为什么这样设计、是否符合 MCP、工具失败如何处理。 | 讲工具粒度贴近任务：高层 `query_database` 封装 schema 获取、SQL 生成、校验、修复、执行，减少模型自行拼接底层 API 的错误分支。MCP 是阶段 02 探索，最终稳定表达是工具适配和工具契约。 |
| Workflow / Agent Workflow | 核心链路：恢复会话与数据库上下文 -> 检索 HDC/SQL Memory/偏好 -> Context Builder -> Agent 工具选择 -> NL2SQL -> validator/repair -> OneDBA 执行 -> SSE 返回 -> 状态持久化。 | 设计自然语言查库 Agent Workflow，覆盖上下文恢复、工具编排、SQL 生成校验、查询执行、流式返回和记忆沉淀。 | 容易被追问“有没有任务规划”“是否支持复杂多步任务”“和普通 API 编排有什么区别”。 | 说明这是面向数据库查询的受控 Workflow，不夸大为通用 Planner。Agent 负责工具选择和多步推进，业务侧通过工具边界、校验器、上下文和取消控制约束执行。 |
| Context Engineering / Prompt Engineering | `build_context()` 组织对话摘要、最近历史、当前数据库、长期记忆、SQL 参考知识库、查询偏好、HDC、SQL Memory，并做 token 估算和预算控制。 | 设计多源上下文构建机制，将会话历史、数据库选择、HDC 语义和 SQL Memory 分段注入 Agent，提高真实业务库查询稳定性。 | 容易被追问上下文过长、污染、冲突和 token 成本。 | 准备讲上下文分层和预算：最近历史截断、SQL Memory token budget、HDC 按 namespace/问题召回、危险 SQL 过滤。也要承认 TTFB 上升是代价。 |
| 后端服务 / API 接入 | 最终版本提供 FastAPI、`/api/chat` SSE、`/api/chat/sync`、`/api/ws`、`/api/sessions`、`/api/hdc`、`/api/admin`、健康检查和 OpenAPI。 | 基于 FastAPI 构建 Agent 后端服务，提供 SSE 流式对话、WebSocket、同步 JSON、会话管理、HDC 和 Admin API。 | 容易被追问并发、取消、错误处理、接口契约。 | 说明项目有 session/user 隔离、cancel registry、WebSocket 断开取消、SSE 事件类型 `step/sql/final/error`、Admin token 控制。不要说高并发生产压测已完成，除非有数据。 |
| 数据库 / 业务系统集成 | 项目面向 OneDBA 平台，使用 `schema_id`、`database_name` 进行库上下文管理；通过 OneDBA API 查询库表结构和执行只读 SQL。 | 将 Agent 接入 OneDBA 业务数据库平台，实现自然语言查库、表结构探索和只读 SQL 查询执行。 | 容易被追问是否直连数据库、权限模型、SQL 注入、安全边界。 | 说明通过 OneDBA API 交互，不是任意直连数据库。只读自动执行，写操作/DDL 有拦截或确认机制。生产还需要平台权限、网络隔离和日志脱敏配合。 |
| SQL 安全 / 权限 / 异常兜底 | validator 做 DDL 拦截、单语句检查、只读约束、表名匹配、字段存在性检查、LIMIT 控制；Admin API 通过 Bearer token，未配置 token 时返回 503。 | 实现数据库 Agent 执行护栏，对 SQL 进行只读、单语句、表/字段和 LIMIT 校验，并为管理端点加入 token 认证。 | 容易被追问是否足够生产安全、写操作如何处理、Admin 删除接口风险。 | 不说已覆盖全部企业安全要求。回答重点：prompt 之外在工具/NL2SQL 层做硬校验；生产仍需更强 RBAC、审计日志、敏感字段脱敏、网络访问控制。 |
| 评测 / 自动化评估 | 评测框架支持测试用例加载、Agent 执行、SQL correctness judge、回答质量 judge、效率评分、HDC 注入审计、JSON/Markdown 报告。阶段 04 主实验 28 条用例：平均分 `92.92% -> 97.49%`，通过率 `26/28 -> 28/28`。 | 构建 Agent 评测闭环，按 SQL 正确性、表/列引用、过滤条件、结果正确性、SQL 规范、工具调用、turns、token 和延迟评估效果。 | 容易被追问是否公开 benchmark、是否 SOTA、judge 是否可靠。 | 明确是项目内 OneDBA 业务库评测集，不是公开 benchmark。评测看完整 Agent 任务，不只看 SQL 文本。说明 baseline vs HDC-SM 是成对对比，收益不能单点归因。 |
| 可观测性 / 链路追踪 | 项目接入 Langfuse；runner 记录 LLM 调用、工具调用、token、tool timing、TTFB、context token、prep_ms 等指标。 | 接入 Agent 可观测链路，记录 LLM 调用、工具执行、token、延迟、TTFB 和上下文准备耗时，支撑问题定位和评测分析。 | 容易被追问观测是否用于线上告警、成本治理、trace 粒度。 | 说明当前主要用于 trace、评测和诊断；不是完整 LLMOps/AgentOps 平台。可以扩展到告警、成本看板、失败分类和灰度对比。 |
| Docker / 部署 / 工程交付 | 项目包含 Dockerfile、docker-compose、Gunicorn 配置、`.env.example`、`DEPLOY.md`、`delivery-checklist.md`、`scripts/acceptance.sh`。最终 README 说明当前形态为 FastAPI + 静态前端 + docker-compose 单机部署。 | 提供 Docker Compose 部署、环境变量配置、健康检查、交付验收、回滚和备份文档，支持从实验验证到单机交付部署。 | 容易被追问是否 K8s 生产化、是否有 CI/CD、是否高可用。 | 稳妥说单机 docker-compose 交付，生产可迁移 K8s/镜像仓库/统一 Secret 管理。不要写已完成大规模分布式或高可用部署。 |
| 工程化落地 / 可交付闭环 | 阶段 04 补齐静态前端、Admin 管理、API 文档、部署文档、验收脚本、评测报告、SQLite 持久化会话/偏好/SQL Memory/Admin 映射。 | 将 Text2SQL Agent 从原型推进到可演示、可评测、可部署、可管理的工程化交付形态。 | 容易被追问真实上线程度、用户规模、稳定性指标。 | 区分“可交付工程形态”和“线上大规模生产系统”。准备说明已有交付要素：Docker、健康检查、Admin、验收、评测、回滚；线上规模和 SLA 不夸大。 |
| 业务场景抽象 / 复杂业务系统 | 文档强调真实业务库中有表名相近、字段语义不透明、枚举口径复杂、多轮追问、SQL 安全和空结果处理等问题；项目把这些抽象为 Agent 工具链、HDC、SQL Memory、validator 和评测体系。 | 面向真实业务数据库查询场景，抽象“找库/找表/理解字段/生成 SQL/安全执行/持续追问”的 Agent 任务链路。 | 容易被追问业务价值、为什么不用普通 BI 或 SQL 模板、是否能迁移到其他业务。 | 回答业务价值在降低陌生库探索成本，不替代专业 DBA/BI。迁移到其他库需要接入 schema 采集、HDC 生成、工具适配、权限和评测用例。 |
| LangChain / LangGraph / ReAct | 阶段 01 使用 LangGraph + FastAPI；阶段 03 使用 OpenAI 兼容 API + 手写 ReAct；阶段 04 使用 deepagents / LangGraph 接管通用循环，并通过 adapter 保留业务边界。 | 具备 LangGraph/deepagents/ReAct Agent 工程实践，能根据服务化控制权和维护成本在框架与业务边界之间做取舍。 | 容易被追问框架细节、为什么不是 LangChain 全托管、手写 ReAct 有什么代价。 | 准备讲阶段演进：原型快、SDK 规范、手写 ReAct 可控、deepagents 降低维护成本。核心判断是控制权边界，而不是追逐框架。 |
| MCP / 工具协议 | 阶段 02 使用 claude-agent-sdk 和进程内 MCP Server 规范工具注册；最终稳定版本更多体现为内部 ToolRegistry + Tool Adapter。 | 有 SDK/MCP 化工具调用探索经验，并在后续版本中沉淀为稳定的内部工具注册和适配层。 | 容易被追问是否实现完整 MCP Server、是否支持外部 MCP 生态。 | 简历中谨慎写“探索/使用 MCP 化工具注册”，不要写完整 MCP 平台。说明最终选择内部工具注册 + adapter，是为了保持业务工具、SSE 和评测契约稳定。 |
| 性能 / 成本优化 | 阶段 04 评测：平均延迟 `48189ms -> 29103ms`，工具调用 `2.6 -> 1.0`，turns `3.3 -> 2.0`，总 Token `28289 -> 18363`；同时 TTFB `4568ms -> 6621ms`。 | 通过 HDC + SQL Memory 降低 Agent 盲搜和重复探索，在项目评测集中减少工具调用、turns、token 和平均总延迟。 | 容易被追问为什么 TTFB 变慢、指标是否稳定、是否线上真实流量。 | 说明 HDC/SQL Memory 检索增加前置准备成本，换来后续探索轮次下降；指标来自 28 条项目评测用例的 paired baseline vs HDC-SM，不是线上大盘。 |
| 前端 / 管理界面 | artifacts 截图显示用户端对话页面有用户/数据库/会话选择、运行状态、SQL 展示、快捷问题；Admin 页面有概览、用户、HDC 管理、SQL Memory。 | 提供配套静态前端和 Admin 管理界面，支持对话演示、SQL 查看、HDC namespace 映射和 SQL Memory 管理。 | 容易被追问前端技术深度、是否完整产品化。 | 把前端定位为工程演示和管理配套，不把它包装成复杂前端项目。重点讲后端 API、状态展示、SQL 可解释性和管理能力。 |

## 简历关键词优先级建议

| 优先级 | 建议突出 | 原因 |
|---|---|---|
| P0 | Text2SQL Agent、Tool Calling、Context Engineering、HDC、SQL Memory、FastAPI/SSE、评测闭环 | 与 AI 应用 / Agent 开发 JD 高频要求高度匹配，且项目证据充分。 |
| P1 | Docker Compose、Admin API、Langfuse 可观测、SQL 安全、业务系统集成 | 能体现工程化落地和后端能力，但不要夸大为完整生产平台。 |
| P2 | MCP、LangGraph、deepagents、ReAct 演进 | 适合面试展开技术取舍，简历上少量出现即可，避免堆框架名。 |
| 避免 | 模型训练、微调、Graph RAG、Multi-Agent、A2A、大规模 K8s 生产化、公开 benchmark SOTA | 当前材料证据不足，容易被追问击穿。 |
