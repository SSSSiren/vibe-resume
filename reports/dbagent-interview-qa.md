# DB-Agent 高压面试 Q&A

面向岗位：AI 应用开发 / Agent 开发 / 大模型应用后端开发

回答口径：基于 `DB-Agent` 项目现有代码和文档，强调手动实现的工程链路、Agent 边界、Text2SQL 真实难点、部署与评测，不虚构用户量、QPS、准确率、降本比例或行业 SOTA。

## 1. 这个项目为什么算 Agent，而不是简单调 LLM API？

### 面试回答

这个项目不是把用户问题直接丢给 LLM 生成 SQL。它有明确的任务目标、工具集合、上下文构建、执行反馈和结果返回链路。用户问一个数据库问题后，系统会先恢复会话和数据库上下文，再检索 Schema 语义、SQL Memory 和历史偏好，由 Agent 决定是否需要找库、找表、查结构、生成 SQL 或执行查询。模型输出不是最终答案，而是驱动工具调用和 SQL 生成流程的一部分。

我认为它算 Agent 的关键点有三个：第一，LLM 不只生成文本，而是参与工具选择和任务推进；第二，工具执行结果会反过来影响后续推理；第三，系统有安全校验、失败修复、记忆沉淀和流式事件返回，形成了一个可控 Workflow。

### 技术要点

- FastAPI 接收用户问题并恢复 `user_id`、`session_id`、`schema_id`、`database_name` 等上下文。
- deepagents / LangGraph 承接通用 Agent 循环和工具调度。
- OneDBA 能力被封装成数据库发现、表搜索、表结构查询、SQL 查询和 SQL 执行工具。
- Context Builder 注入会话历史、HDC、SQL Memory、查询偏好等信息。
- SSE 返回 `step`、`sql`、`final` 等过程事件，而不是只返回一段文本。

## 2. Text2SQL 的完整链路是什么？

### 面试回答

完整链路是：用户自然语言问题进入后端后，服务先恢复会话和当前数据库上下文；然后根据问题检索 HDC Schema 语义和 SQL Memory；Agent 根据上下文决定调用找表、查结构或查询工具；查询工具内部会获取真实 Schema，调用 NL2SQL 生成 SQL；SQL 生成后进入 validator 做只读、安全、表名和字段校验；校验通过后通过 OneDBA API 执行；失败时进入 repair 尝试修复；最后把 SQL、结果摘要、工具步骤和最终回答通过 SSE 或 JSON 返回，并沉淀会话状态和 SQL Memory。

这个链路的重点不是“生成 SQL”单点，而是把 Schema 获取、Agent 决策、SQL 校验、数据库执行和结果反馈串成一个后端可控流程。

### 技术要点

- 输入层：FastAPI `/api/chat`、同步接口、WebSocket、session API。
- 上下文层：会话历史、查询偏好、HDC、SQL Memory。
- Agent 层：工具选择、事件适配、流式输出。
- NL2SQL 层：SQL 生成、Schema 富化、校验、失败修复。
- 执行层：OneDBA API 只读查询。
- 结果层：SSE / WebSocket / JSON 返回步骤、SQL、结果和最终回答。

## 3. Schema 信息怎么进入上下文？

### 面试回答

项目里有两条 Schema 进入上下文的路径。一条是运行时路径：Agent 可以通过工具查数据库列表、搜索表、获取表结构，拿到真实 Schema 后再生成 SQL。另一条是前置语义路径：HDC 会离线采集 OneDBA 的 Schema、字段注释、样例值和枚举信息，生成列级、表级、库级语义描述，存入 OpenViking；在线查询时按用户问题召回相关 Schema 语义，再注入 Agent 上下文和 NL2SQL 流程。

这两条路径的分工是：HDC 提供更早的业务语义线索，帮助少猜表、少查结构；运行时工具保证最终使用的 Schema 是真实的，不能只依赖召回文本生成 SQL。

### 技术要点

- HDC 是列级、表级、库级三层 Schema 语义索引。
- OpenViking 用于存储和检索 HDC 语义上下文。
- Context Builder 负责把 HDC 命中结果和会话上下文组装给 Agent。
- `describe_table` / Schema 工具用于获取真实表结构。
- HDC 不替代实时 Schema 校验。

## 4. Tool Calling 在项目里解决了什么问题？

### 面试回答

Tool Calling 解决的是模型和真实数据库系统之间的边界问题。LLM 本身不知道当前有哪些库、哪些表、字段怎么定义，也不能直接访问 OneDBA。所以我把数据库能力封装成工具，让 Agent 在需要信息或需要执行动作时调用工具，而不是让模型凭空编表名、字段名或结果。

另外，工具层还能放工程约束。比如 `query_database` 这种高层工具把 Schema 获取、SQL 生成、校验、修复和执行封装在一个稳定边界里，减少 Agent 反复调用底层工具试错。

### 技术要点

- 工具包括数据库发现、表搜索、表结构查询、NL2SQL 查询、SQL 执行、HDC 相关操作。
- 阶段 02 用 SDK/MCP 规范工具注册。
- 阶段 03 用手写 ReAct 拿回工具执行控制。
- 阶段 04 用 Tool Adapter 适配 deepagents / LangChain。
- 高层工具降低 Agent 决策轮次，底层工具保留必要探查能力。

- 哪些工具适合暴露给 Agent，哪些逻辑应该放工具内部？

## 5. 如何防止生成危险 SQL？

### 面试回答

我没有只靠 prompt 约束 SQL 安全，而是在执行前做硬校验。项目里会限制自动执行的 SQL 类型，只允许只读查询，比如 `SELECT`、`SHOW`、`DESCRIBE` 这类语句；对 `CREATE`、`ALTER`、`DROP`、`TRUNCATE` 等 DDL 语句做拦截；同时检查单语句、表名、字段、LIMIT 等约束。SQL 只有通过 validator 后才会进入 OneDBA 执行。

如果是面试里的安全追问，我会强调：LLM 生成 SQL 不能直接信任，执行权限必须收在后端工具层和数据库代理层，prompt 只能作为辅助约束。

### 技术要点

- SQL 执行前经过 validator。
- 只读语句白名单：`SELECT` / `SHOW` / `DESCRIBE`。
- DDL 和高风险操作拦截。
- 单语句校验，避免多语句拼接。
- 表名、字段和 LIMIT 校验，减少越权和大查询风险。

### 可能被继续追问的点

- 如果模型生成 `SELECT ... INTO` 或隐式写操作怎么办？
- 是否做了用户级表权限和字段脱敏？
- SQL 注入和自然语言诱导攻击如何处理？

## 6. SQL 执行失败怎么处理？

### 面试回答

SQL 失败分两类处理。第一类是执行前失败，比如 SQL 类型不允许、表名字段不合法、缺少 LIMIT，这类不会执行，会直接进入校验错误或修复流程。第二类是执行时失败，比如字段不存在、语法错误、类型不匹配、空结果或 OneDBA 返回错误，系统会把错误信息作为上下文交给 repair 流程尝试修复，再重新校验和执行。

但我不会把 repair 说成万能机制。它适合修复语法、字段引用、简单条件这类问题；如果一开始业务口径理解错了，还是要靠 HDC、Schema 工具和评测归因来改进。

### 技术要点

- `validate_sql` 负责执行前校验。
- `repair_sql` 在失败时尝试修复 SQL。
- 修复后仍要重新走安全校验。
- OneDBA 执行错误会作为修复上下文。
- 最终失败需要把错误原因通过事件或响应返回，而不是静默吞掉。

### 可能被继续追问的点

- repair 最多重试几次？
- 如何避免失败后无限循环？
- 空结果到底算失败还是正确查询？

## 7. 多轮对话下如何管理上下文？

### 面试回答

多轮对话不是简单把所有历史消息拼进 prompt。项目里会通过 session 恢复用户、数据库、当前 schema、会话历史和查询偏好，同时维护 SQL Memory。新的问题进来时，Context Builder 会把最近对话、当前数据库、HDC 召回结果、历史成功 SQL 模式和查询偏好组合成上下文。

这里我做了一个取舍：SQL Memory 复用的是查询模式，不是最终答案。比如上一次成功查过“按天统计告警数量”，下一次问相邻时间范围时，可以参考历史 SQL 的事实表、时间字段和聚合方式，但仍要重新生成、校验和执行 SQL。

### 技术要点

- session 维持多轮会话状态。
- 查询偏好记录用户在数据库选择、查询口径上的偏好。
- SQL Memory 存储成功问题、SQL、表名、数据库、执行摘要和 embedding。
- Context Builder 控制哪些上下文进入 Agent。
- 需要 token budget，不能无限追加历史。

- SQL Memory 如何防止错误经验污染？

## 8. 和普通 RAG 问答有什么区别？

### 面试回答

普通 RAG 问答通常是从文档里召回片段，再让模型生成文本答案；DB-Agent 的目标是对真实数据库做查询。它可以使用类似 RAG 的检索能力，比如 HDC 和 SQL Memory，但召回内容只是帮助选表、理解字段和复用 SQL 模式，最终还要生成 SQL、校验 SQL、执行数据库查询，再基于真实结果回答。

所以它的评估也不同。普通 RAG 更关注答案是否忠实于文档；Text2SQL Agent 要关注表列引用是否正确、过滤条件是否正确、SQL 是否安全、执行结果是否符合问题，以及工具调用、延迟和 token 成本。

### 技术要点

- RAG：文档召回 -> 文本回答。
- DB-Agent：Schema/SQL 模式召回 -> Agent 工具调用 -> SQL 生成/校验/执行 -> 结果回答。
- HDC 类似结构化 Schema RAG，但不是最终答案来源。
- SQL Memory 是 few-shot 查询模式，不是答案缓存。
- 评测维度包括 SQL 正确性、执行结果、工具调用、延迟、token。

### 可能被继续追问的点

- HDC 算不算 RAG？
- SQL Memory 和向量知识库有什么区别？
- 如果召回结果和真实 Schema 冲突，信哪个？

## 9. 如果数据库表很多，Schema 太长怎么办？

### 面试回答

不能把全库 Schema 一次性塞进上下文。我的处理思路是分层和按需：离线先把 Schema 做成列级、表级、库级语义索引，在线只按问题召回相关库表字段；Agent 需要进一步确认时，再调用表搜索和表结构工具拿真实 Schema。这样上下文里进入的是和问题相关的候选表、关键字段和少量业务语义，而不是全量 DDL。

同时 SQL Memory 可以减少重复探索。相似问题如果过去已经成功查过，系统可以召回历史 SQL 模式，让 Agent 更快停在正确事实表和查询模式上。

### 技术要点

- 三层 Schema 语义索引：列级、表级、库级。
- OpenViking 按问题召回相关 HDC。
- 运行时工具按需查表结构。
- Context Builder 做上下文组装和 token 控制。
- SQL Memory 复用相似查询模式，减少找表和查字段轮次。

## 10. 如何评估生成 SQL 的正确性？

### 面试回答

我不会只看 SQL 字符串是否和参考 SQL 一样，因为同一个问题可能有多种等价写法。项目评测更关注是否能在真实业务库用例上生成可执行、安全且语义正确的 SQL，并返回符合问题的结果。具体看通过用例、表/列引用、过滤条件、SQL 执行结果、工具调用次数、延迟和 token。

最终简历里的量化数据是基于项目内 28 条真实业务库评测用例，并且是和 02-SDK-DBAgent 阶段测试数据对比：通过用例从 `20/28` 到 `28/28`，平均延迟从 `106727ms` 到 `29103ms`，平均工具调用从 `5.7` 到 `1.0`，总 token 从 `34603` 到 `18363`。这些只说明项目内场景的工程改进，不包装成公开 benchmark。

### 技术要点

- 评测用例来自项目内真实业务库场景。
- 不只比较 SQL 文本，还看执行结果和业务语义。
- 指标包括通过用例、延迟、工具调用、token。
- 评测报告用于发现 schema linking、过滤条件、结果正确性问题。
- 不声称 Spider/BIRD SOTA 或通用准确率。

### 可能被继续追问的点

## 13. 最大技术难点是什么？

### 面试回答

最大难点不是 SQL 语法，而是把真实业务库的 Schema 语义、Agent 工具决策和工程可控性放到一条稳定链路里。真实用户不会告诉你准确表名和字段名，他们说的是业务词，比如工单、告警、状态、时间范围。系统要先选对事实表和字段，再生成安全 SQL，否则 SQL 写得再规范也没有意义。

所以我引入 HDC 把 Schema 语义前置，减少从零找表；引入 SQL Memory 复用历史成功查询模式；同时在工具和 validator 层做安全限制。这个难点是语义、工具和工程控制的组合问题。

### 技术要点

- Schema linking 是核心难点。
- HDC 解决库表字段的业务语义线索。
- SQL Memory 解决相似查询模式复用。
- 工具粒度影响 Agent 是否频繁试错。
- validator 保证执行前安全边界。

## 14. 这个项目目前有什么不足？

### 面试回答

这个项目还有几个明确不足。第一，评测集是项目内真实业务库用例，不是公开 benchmark，所以不能证明通用 Text2SQL 能力。第二，HDC 和 SQL Memory 会增加上下文准备成本，文档里也记录了 TTFB 上升的问题。第三，SQL Memory 需要治理，历史成功 SQL 如果过期或质量不高，会污染后续上下文。第四，当前安全主要覆盖只读、DDL 拦截、表字段校验和 LIMIT，用户级权限、敏感字段脱敏、审计和 RBAC 还可以继续加强。

另外，Docker Compose 能支持内部部署和演示交付，但还不是完整云原生生产体系。

### 技术要点

- 评测不是公开 benchmark。
- HDC / SQL Memory 有前置成本。
- TTFB 上升需要继续优化。
- SQL Memory 需要质量标记、过期清理和错误隔离。
- 权限、脱敏、审计、K8s、CI/CD 仍是后续方向。

## 15. 如果投到字节/阿里/腾讯这类 AI 应用开发岗，你怎么解释匹配度？

### 面试回答

我会从岗位关键词对齐，而不是泛泛说“做过大模型”。这个项目覆盖 AI 应用后端的几个关键能力：第一，有 Agent 工具调用和 Workflow，不是单轮 prompt；第二，有 Text2SQL 和真实数据库交互，涉及 Schema、SQL 校验和只读执行；第三，有类似 RAG 的 Schema 语义检索和 SQL Memory，但最终落到可执行工具链；第四，有 FastAPI、SSE、Docker Compose、Admin、Langfuse 和评测脚本，说明我做的不只是 demo，还有工程交付和迭代闭环。

我也会主动说明边界：它不是通用 Agent 平台，也不是模型训练项目，而是一个围绕数据库问答场景手动实现的大模型应用后端项目。这种表述更真实，也更容易经得住代码追问。

### 技术要点

## 16. 为什么阶段 02 用 SDK，后面又切到手写 ReAct？

### 面试回答

阶段 02 用 SDK/MCP 的目的，是把工具注册、消息循环和 Agent 调用边界规范起来。这个阶段的价值是让我更清楚地定义工具 schema 和 SSE 事件转换。但服务化之后，SDK 的封装也暴露了问题，比如资源释放、取消控制、异常处理、事件细节、token 和 timing 统计不够可控。

数据库 Agent 和普通聊天不一样，用户断开连接、SQL 执行失败、工具超时、取消任务、统计成本都需要业务代码能干预。所以阶段 03 我切回 OpenAI-compatible API + 手写 ReAct，把 LLM 调用、工具执行和事件输出拿回业务代码控制。阶段 04 再用 deepagents 接管通用循环，但保留业务边界。

### 技术要点

- 阶段 02：SDK/MCP 规范工具和消息。
- 问题：运行时黑盒、取消和资源控制弱、观测粒度不足。
- 阶段 03：手写 ReAct 提高控制权。
- 阶段 04：deepagents 降低通用循环维护成本。
- 核心经验：框架负责通用循环，业务代码负责数据库安全和效果边界。

## 17. HDC 和 SQL Memory 分别解决什么问题？

### 面试回答

HDC 解决的是“这个数据库、表、字段是什么意思”。它把 Schema 语义前置到离线阶段，生成列级、表级、库级描述，在线时召回相关上下文，帮助 Agent 更快找到正确表和字段。

SQL Memory 解决的是“类似问题以前怎么查成功过”。它记录成功问题、SQL、表名、数据库和执行摘要，新问题召回相似 SQL 模式作为 few-shot 参考。它不是答案缓存，当前问题仍然要重新生成、校验和执行 SQL。

### 技术要点

- HDC：Schema 语义层，面向库表字段理解。
- SQL Memory：查询模式层，面向历史成功 SQL 复用。
- HDC 存储和检索基于 OpenViking。
- SQL Memory 基于 SQLite 持久化。
- 两者都进入上下文，但都不能绕过真实 Schema 和 SQL 校验。

- HDC 命中不准时怎么降级？
- SQL Memory 命中相似但业务口径不同怎么办？
- 两者的 token budget 如何分配？

## 18. 如果面试官质疑“这不就是 Workflow，不是 Agent”，你怎么答？

### 面试回答

我会承认它不是完全开放式通用 Agent，而是一个受控的数据库查询 Agent。它确实有固定业务 Workflow，比如必须经过 SQL 校验和只读执行；但在 Workflow 内部，Agent 会根据上下文决定是否需要找表、查结构、生成查询或执行 SQL。这个项目的目标不是追求最大自由度，而是在数据库场景里让 LLM 的决策空间受工具和安全边界约束。

所以我会把它定位为“面向 Text2SQL 的受控 Agent Workflow”。这比说成通用 Agent 平台更准确，也更符合真实代码。

### 技术要点

- 有固定安全和执行链路。
- Agent 在受控范围内做工具选择和任务推进。
- 高层工具封装减少无意义自由探索。
- 数据库场景需要强约束，不适合完全开放工具调用。
- 真实表述：受控 Agent Workflow。

## 19. 如何解释 OpenViking 在项目中的作用？

### 面试回答

OpenViking 在这个项目里主要承担 HDC 的语义存储和检索。离线阶段把 OneDBA Schema、字段注释、样例值和枚举信息加工成列级、表级、库级语义描述后，写入 OpenViking；在线阶段根据用户问题召回相关 Schema 语义，作为 Agent 和 NL2SQL 的上下文。

我不会说 OpenViking 直接保证 SQL 正确。它提供的是召回能力和上下文载体，真正的 SQL 正确性还要靠真实 Schema 获取、NL2SQL、validator、执行结果和评测闭环共同保证。

### 技术要点

- OpenViking 用于 HDC 语义索引的存储和检索。
- 离线写入，在线召回。
- 召回内容是 Schema 业务语义，不是最终答案。
- 与 Context Builder、HDC Retriever 配合使用。
- 与 SQL Memory 分工不同。

## 20. 如果继续优化，你会先做什么？

### 面试回答

我会优先做三件事。第一，补失败归因，把错误分成选错表、字段错、过滤条件错、SQL 规范问题、空结果误判、工具超时等类型，这样优化才有方向。第二，治理 HDC 和 SQL Memory，记录召回命中、最终是否采用、历史 SQL 质量和过期情况，避免上下文污染。第三，补强安全和权限，比如用户级表白名单、敏感字段脱敏、审计日志和更细粒度 RBAC。

如果进入生产级部署，再补 K8s、Secret 管理、CI/CD、监控告警和多实例会话存储。但这些我不会提前包装成已经完成。

### 技术要点

- 评测从结果分数扩展到失败归因。
- HDC 需要命中审计和过期更新。
- SQL Memory 需要质量治理和隔离。
- 安全补 RBAC、脱敏、审计。
- 部署补 K8s、Secret、CI/CD、监控告警。
